# Architecture

Developer reference. What players see is documented in the [wiki](wiki/Home.md); update it alongside any user-visible change here (see [`AGENTS.md`](../AGENTS.md)).

MinePanel is a client-only Fabric mod, a loopback-only local service, and a static browser application embedded in the mod JAR. Minecraft APIs belong in the client adapter; the browser consumes versioned snapshots and never issues gameplay mutations.

The client adapter owns lifecycle and reads Minecraft state on the client thread. It copies state into immutable snapshots before publishing to bounded background service workers. The service serves only bundled resources and narrowly scoped authenticated read-only data. Optional integrations are separate adapters; absence or failure is reported as unavailable and does not prevent startup.

Gameplay history is session-only and bounded to 100 immutable events. Open/last-viewed containers and pins remain unimplemented. Chat is not retained. Layouts, preferences and rules are configurable (see [Layout and rules](#layout-and-rules)).

Client tick sampling is capped at four samples per second, suppresses unchanged values, and writes immutable versioned position/dimension/health snapshots into an atomic store. The browser WebSocket receives a full initial snapshot followed by changed-field deltas and reconnects after disconnect. HTTP state access uses a bearer token; the browser session endpoint sets the same random per-server token as an HttpOnly cookie for WebSocket authentication, never in a URL. Both listeners bind to IPv4 loopback; Host and Origin are checked, WebSocket handshakes and frames are bounded, and only read-only paths/frames are supported. No network, disk, or expensive calculation belongs on the Minecraft tick/render thread.

Current player fields include position, dimension ID, health, maximum health, absorption, active-session duration, inventory/equipment, vanilla statistics and session history. The target client has not been compiled or run in Minecraft in this environment.

## Layout and rules

The dashboard layout (tiles, settings, profiles, pinned windows, update rate and rules) is stored by the mod as `config/minepanel/layout.json`. It is read and written through the authenticated `/api/layout` endpoint and validated on both sides: `normalizeLayout` in `layout.js`, and `LayoutStore` with `LayoutRules` in Java. Both must accept and reject the same layouts, and the shared cases in `src/test/fixtures/layouts-v2.json` are checked by both test suites. Rules are evaluated only in the browser (`rules.js`), against the snapshots it already receives. They never cause gameplay actions.

Layout version 2 (rules v2, see [RULES_V2.md](RULES_V2.md)) is current.

- **Version 1** is still read, and the browser converts it. On the first version 2 save over a version 1 file, the mod copies the old file to `layout.v1-backup.json` and never overwrites that copy.
- **Saving** accepts only version 2.
- **A stored file that fails validation** loads as nothing. It is first copied to `layout.rejected.json`, so a later save can't lose it.
- **A version 1 file the browser can't convert** stays untouched: the dashboard shows the error and doesn't save until a layout is imported.

Schema version 5 adds two detail fields for rules (phase 4), each replaced whole when it changes:

- **`sensors`**: `moonPhase`, `spawnDistance`, `air`, `maxAir`, `armor`, the flags `onFire`, `inWater`, `inLava`, `inRain`, `sneaking`, `sprinting`, `sleeping`, `bossBar` and `raid`, plus `riding`, `using`, `light`, `look`, `nearby` and `screen`. `light`, `look`, `nearby` (living entities, at most 128, nearest first) and `screen` are null unless an enabled rule reads them. The mod works that out from the saved layout (`LayoutRules.needs`). The entity scan runs at most twice a second, within the largest radius asked for, capped at 64 blocks and at the render distance. Everything is read on the client thread at sampling time. Boss bars are read through a read-only accessor mixin.
- **`registries`**: items, blocks, entity types, effects, biomes and general statistics as `{ id, name, icon }`, at most 4096 per kind, for the rule editor's pickers. They are listed once per connection (and after a resource reload), so they travel with the initial snapshot and almost never in an update. Their icons are rendered only when the dashboard first requests one.

See [RULES_V2.md](RULES_V2.md#phase-4-2026-10-16) for the conditions that read them.

## Inventory and equipment protocol

Schema version 2 now includes `inventory`, `statistics` and `history`; both HTTP/WebSocket envelopes and player states use version 2. Unsupported versions require a fresh compatible dashboard, not silent interpretation. An available inventory contains exactly 36 indexed `slots`: 0–8 are hotbar, 9–35 are main inventory. `selectedHotbarSlot` is 0–8. `equipment` has `head`, `chest`, `legs`, `feet`, `offhand`, and `mainhand`. Mainhand is the same immutable value as the selected hotbar item, so the summary and slot cannot disagree.

Each item contains `empty`, registry `itemId`, readable `name`, `count`, `maxCount`, `damage`, `maxDamage`, derived `remainingDurability`, and `enchantments` (`id`, readable `name`, `level`). Empty items have null identity/name/durability, zero counts, and no enchantments. Non-damageable items have null durability rather than fabricated zero durability. Only explicit value records cross the thread boundary; arbitrary Minecraft objects/components are not serialized.

Initial messages contain a complete snapshot. Updates include `baseRevision` (the last revision sent to that connection); revisions can skip because sampling coalesces changes. Inventory updates carry only changed `{index,item}` slot entries, a changed selection, and changed equipment keys. Unchanged inventory is omitted entirely. Availability transitions carry all fields, with `inventory:null` on world disconnect. The browser validates and applies a complete update atomically; missing/wrong baselines or unsupported schemas close the socket and reconnect for a fresh full snapshot. Transport disconnect clears displayed live values, not merely the connection badge.

The client samples every 1, 2, 5, 10 or 20 client ticks (20, 10, 4 by default, 2 or 1 times per second), chosen under "Updates" while customizing and saved as `updates.intervalMillis` in the layout; a save takes effect on the next tick. It compares lightweight immutable values. Network serialization and writes occur only on service workers; inventory is not serialized every tick. The adapter reads only on the client tick thread, retaining no player/world/screen references after the sample. Brief changes between samples can be missed. Browser rendering updates changed slot nodes using text, never item-provided HTML. Item sprites, inventory actions, and warning rules are not implemented.

MinePanel exposes no slot-click, equip, consume, item-move, or inventory-changing packet operation. Its inventory adapter only reads stacks. HTTP and WebSocket threads never read live Minecraft objects.

### Container contents and Sophisticated Backpacks

`contents` is null for items that hold nothing, and lists up to 128 held items (one level deep) for shulker boxes (27 slots, empties included), bundles and backpacks (by slot, empties included, padded to the backpack's `BackpackItem.getNumberOfSlots()`; remembered empty slots are stored as `{}` in the WorldStore). `contentsUnknown` (always present) is true only for a backpack whose contents MinePanel hasn't seen; `contents` is then `[]`. Java (`ItemSnapshot`) and `protocol.js` reject any other combination.

Backpacks go through `Backpacks` (client, all nodes), a facade that does nothing unless, on NeoForge, `ModList` has `sophisticatedbackpacks` at or above `sophisticatedbackpacks_minimum` from MinePanel's `[modproperties.minepanel]`. `dev.craftyplayz.minepanel.backpacks.SophisticatedBackpacks` (NeoForge only) is the only code importing `net.p3pp3rf1y` (`litematicaIsolation` enforces it). Any `LinkageError`/`RuntimeException` turns it off for the session with one warning.

Facts it relies on (Sophisticated Backpacks 3.25.34 / Core 1.4.11, read from the JARs): a backpack is a `BackpackItem`; its stack carries `ModCoreDataComponents.STORAGE_UUID` (network-synced) once first opened, and `ModDataComponents.LOOT_TABLE` while it's an unopened loot backpack. The items live in the overworld saved data `"sophisticatedbackpacks"` (`BackpackStorage`, a private `Map<UUID, CompoundTag>`), under `contents.inventory.Items[]` with a `Slot` each, encoded with `CodecHelper.OVERSIZED_ITEM_STACK_CODEC`. `BackpackStorage.get()` and `getOrCreateBackpackContents` create entries and mark the data dirty, so MinePanel uses neither.

- **Singleplayer:** at most every 3 s (immediately for a newly seen backpack), and only for backpacks the sampler has seen, the client thread queues one task with `MinecraftServer.execute`. On the server thread (the task returns if `execute` ran it inline) it gets the existing data with `DimensionDataStorage.get` (never `computeIfAbsent`), serializes it with the side-effect-free `save(new CompoundTag(), …)`, decodes new stacks for the requested UUIDs and hands them to the client thread with `Minecraft.execute`. A UUID without an entry holds nothing.
- **Any world:** while a `BackpackContainer` is open (every 10 ticks and once as it closes), the stacks in its `realInventorySlots` are encoded with the same codec and stored with `WorldStore.putBackpack`, keyed by `getStorageWrapper().getContentsUuid()`. The world file keeps up to 64 backpacks (`backpacks: [{uuid, seenAt, items}]`), forgetting the one stored longest ago.
- Counts are capped at `ItemSnapshot.MAX_COUNT` for stack-upgraded backpacks. Server results win over remembered ones. Unchanged contents keep the same `Backpacks.Contents` instance, which is part of `MinecraftInventoryCollector`'s item cache key, so tooltips are only rebuilt when the contents change.

**Placed Sophisticated Storage blocks** (only when `sophisticatedstorage` is loaded, and only together with a supported Sophisticated Backpacks, since they share the `Backpacks` source; no minimum version check, any failure turns off only storages with one warning). `backpacks/SophisticatedStorage` is the only class touching `net.p3pp3rf1y.sophisticatedstorage`. Facts read from the 1.5.30.1535 JAR with `javap`:

- Every chest, barrel, limited barrel and shulker box is a `StorageBlockEntity`; its `getStorageWrapper()` (`block.StorageWrapper`) keeps the items in a contents tag, `inventory.Items[]` with a `Slot` each, `CodecHelper.OVERSIZED_ITEM_STACK_CODEC` (the backpack format). `StorageWrapper.save(new CompoundTag())` only copies that tag and writes plain fields, so it is the read path. Not used: `getInventoryHandler()` (creates the handler lazily), `getNumberOfInventorySlots()` (saves the default size and marks the block dirty when unset), the block entity's `saveAdditional` (its `saveSynchronizedData` clears a render flag) and `LevelChunk.getBlockEntity(pos)` (can promote a pending block entity).
- Slot count: the saved `numberOfInventorySlots`, else `getDefaultNumberOfInventorySlots()` (from the block). Name: `getDisplayName()` (custom name, else the wood or block name). Double chests: the second half (`ChestBlockEntity.isMainChest()` false) holds nothing; the main half's wrapper has both halves' slots, and storages are keyed by `getMainPos()`.
- The id is `UUID.nameUUIDFromBytes("<dimension>|x|y|z")`, so breaking and replacing a storage keeps it, and moving it does not.
- **Singleplayer:** with the backpack read (the same `server.execute` task), every 5 s the index walks the chunks within the server view distance of each player (`ServerChunkCache.chunkMap.getVisibleChunkIfPresent` + `ChunkHolder.getTickingChunk()`, so only loaded, ticking chunks; nothing is loaded or generated), collects storages from each chunk's block entity map, keeps the 256 nearest and copies their wrapper tags. Watched storages (selected or listed in `shown`) are re-read every 250 ms by position, only that block entity; when their chunk isn't loaded the last contents stay (never read: `contentsUnknown`).
- **Any world:** a `StorageContainerMenu` screen (including limited barrels) is captured every 5 ticks and once as it closes from `realInventorySlots`; `getStorageBlockEntity()` gives the position on the client (the menu is built from the position sent with it). In singleplayer this only adds who opened it and when; on servers these are the listed storages. They are kept in memory for the session only (WorldStore saves backpacks only), at most 64.
- The list holds backpacks first, then storages (opened ones newest first, then nearest), 256 in total; storage contents beyond 128 slots are cut off.

Applied and stored/book enchantment components are merged by registry ID with the higher level and sorted for stable comparisons. Readable text is bounded to 256 UTF-16 units without splitting surrogate pairs; controls are replaced and malformed Unicode is repaired. Metadata exceeding the bounded protocol invariants makes the sample unavailable rather than crashing gameplay or publishing partially copied inventory; a generic warning is logged once, without item contents.

JourneyMap is the only map source; MinePanel does not render terrain. Litematica completion is based on the compared world state, never carried inventory (see below). JourneyMap's compatible versions and iframe behavior remain unverified until tested against Minecraft 26.1.2.

## Extraction, statistics and session events

`MinecraftInventoryCollector` wraps live stacks in getter-only `ItemExtractor.ItemView` adapters. The pure Java extractor handles empty stacks, metadata bounds, durable/non-durable items and applied/stored enchantment merging before immutable snapshot construction. Fake-view unit tests exercise this production transformation, not real Minecraft stacks; there is no configured game-test or headless client source set.

`MinecraftStatisticsCollector` reads `LocalPlayer.getStats()` only for ten custom statistic IDs actually observed in this connection's vanilla statistics packets. A client-only `StatisticsSyncMixin` observes `ClientPacketListener.handleAwardStats` at RETURN, after vanilla's thread handoff and application. Sparse responses add synchronization evidence rather than replacing it; absent values remain null. The bounded evidence set and static ID map retain no stack/player/world references. A standard `REQUEST_STATS` asks for server-maintained counters; it does not change inventory or gameplay. No custom server plugin or bypass is used.

`StatisticsTracker` establishes a separate baseline on the first received value of each counter. A decrease invalidates/rebases that counter; a new connection resets all baselines. Session means *since first synchronization*, not guaranteed since join. Distance is transmitted in centimeters and time in ticks, formatted in the browser as meters/durations. Cumulative means this server/world's totals, not universal account statistics. Counters are read at four Hz, requests at most every ten seconds; unchanged fields are suppressed. Unknown values stay null even after an empty response, as vanilla packets lack a completeness marker.

`GameplayTracker` owns an oldest-first deque; insertion evicts the oldest event at 100. Events contain increasing session-local IDs, wall-clock timestamps, categories, labels and bounded details. The browser displays newest first and preserves expanded details for unchanged event IDs. Death/dimension transitions are observed at END_CLIENT_TICK to avoid the slower telemetry sampling window; only tiny comparisons/event insertion happen there. Serialization, sockets and dashboard rendering stay off the client thread. Very brief transitions between ticks and unobserved/server-hidden deaths are not inferred.

Fabric play JOIN defines a new session, including joining another server/world; respawn or dimension travel within the same connection does not reset history/baselines. DISCONNECT appends one lifecycle event and retains an inactive history until the next JOIN. A transient missing player/level or invalid metadata clears live availability without prematurely resetting the connection session. Kill events describe aggregate reported counter increases only, with observation timestamps and unknown targets; the initial cumulative total is never treated as a new kill. No chat parsing, permanent history, database, disk write, scoreboard inference, or charts are involved.

Fabric disconnect notification can arrive on the network thread. MinePanel schedules its state changes onto the client executor, ignores obsolete listener callbacks, and samples only the joined, matching connection. A lingering player/level after disconnect cannot restart or erase the retained session.

Statistics and history deltas replace their whole bounded objects only when changed; inventory keeps its existing changed-slot delta semantics. Availability transitions send all fields with `statistics:null`, `inventory:null` and inactive retained history. Transport loss clears even stale displayed history until a fresh initial snapshot arrives. Unit tests cover baseline changes, unavailable counters, bounds, serialization, revision suppression and reset semantics; packet injection and live client compatibility remain unverified pending an accessible Minecraft build environment.

## Client frame rate

`FrameTimingMixin` calls `FrameCollector` at every return from `Minecraft.runTick`, which renders one frame, so frame time is measured end to end, including menus, loading screens and framerate-limiter waits. `FrameStats` runs on the render thread and allocates nothing per frame. It counts each frame into the second it ended in and into a log-spaced frame-time histogram with buckets 2% wide (0.1 ms to 10 s). Each closed second keeps only its non-empty buckets, in a 600-second ring. Running merges for the 10 s, 30 s, 60 s and 600 s windows add the new second and subtract the one leaving. A window's average is frames divided by their total duration. Its 1% low is the frame rate at the 99th-percentile frame time, accurate to the bucket width. A stall shows as seconds with zero frames.

The snapshot is the `performance` detail field. It holds frames per second for up to 600 seconds (newest last) and `{seconds, average, low}` per window, or null until the first second closes. It is rebuilt and resent only when a second closes. The browser averages long windows into at most 120 points and draws them with monotone cubic interpolation, so the curve never overshoots the data. The chosen window is saved as `settings.performance.window`. The mixin's injection into 26.1.2's `runTick` is unverified until the client compiles.

## 3D render

The `appearance` detail field (added within schema version 5; the dashboard and mod ship together) is `{ skin, slim, armor: [ { slot, model, texture, color } ], rightHand, leftHand }`, replaced whole when it changes. `AppearanceCollector` reads it on the client thread at sampling time and caches everything until the resource packs reload:

- **Skin:** a downloaded skin is copied out of the `DynamicTexture` the game already holds (already converted from legacy 64×32 skins) and encoded to PNG once per skin. A default skin is read from the resource packs. Either is served at `/texture/<key>.png`; keys hash the contents or the resource path and the icon epoch, so they are cached as immutable. `skin` is null while the skin can't be read.
- **Armor:** for each worn item's `equippable` asset, the layers of `assets/<ns>/equipment/<path>.json` (decoded with `EquipmentClientInfo.CODEC`, as `EquipmentAssetManager` loads them) for `humanoid`, `humanoid_leggings` (legs) and `wings` (chest). Colours follow `EquipmentLayerRenderer.getColorForLayer` (dyed leather, and undyed dyeable layers without a default are skipped). Elytra layers that use the player's texture take the skin's elytra or cape when there is one. Trims and the enchantment glint are left out.
- **Held items:** the inventory icon key, whether the icon is a flat sprite (`!usesBlockLight`), and the item model's third-person transform for that hand, read through the `ItemRenderStateAccessor` and `ItemLayerRenderStateAccessor` mixins and mirrored for the left hand as `ItemTransform.apply` does. Arms follow `getMainArm()`.

Any failure here (including a mixin that no longer applies) logs one warning and sends an empty appearance; the rest of the sample is unaffected.

`model.js` draws it with plain WebGL (the page's CSP allows no outside scripts). Parts are built as `ModelPart.Cube` builds them: the same texture net, pivots and armor deformations (outer armor 1, leggings 0.5, legs 0.1 less, left limbs mirrored), with the wide or slim arms. Held items are the icon extruded as the item model generator does (a one-pixel slab with walls at opaque edges, at the sprite's own resolution), placed as `ItemInHandLayer` places them; block icons are drawings rather than sprites, so they are held as an upright card. Arms take the item-holding pose and the idle bob. Lighting is entity-like: 40% ambient plus two fixed lights, with cut-out transparency.

The orientation is a swing (any tilt) times a twist about the spin axis. Dragging turns it about the screen's axes. While spinning, a released model waits 0.8 s, then speeds up over 2 s while the swing eases back to none, so it rights itself without changing which way it faces. With spinning off it stays where it was left. The model is redrawn with `requestAnimationFrame` only while its tile is visible; with reduced motion it doesn't spin or bob.

## Litematica build progress

Schema version 4 adds the `build` detail field, replaced whole when it changes:
`{ available, reason, placement: { id, name, total, placed, wrong, extra, uncheckedChunks, scanComplete, checkedAt } | null, materials: [ { itemId, name, icon, left, have } ] }` (at most 128 materials). `reason` is `missing`, `version` or `error` when unavailable, `none` when no placement is selected and `counting` while the schematic's blocks are counted; it is null when a placement is shown.

Code is split in three so Litematica's absence can never break class loading:

- `dev.craftyplayz.minepanel.build` (main source set, pure Java, no Minecraft): `BuildTracker` (counting, chunk scanning, per-chunk cache, materials), `BuildRules` (per-position classification), `ChunkCounts`, the `BuildSource` interface it reads through, and the `BuildProgress` snapshot. Tested by `BuildProgressTest` with fake placements.
- `dev.craftyplayz.minepanel.litematica` (client): `LitematicaBuildSource`, the **only** code that imports Litematica/MaLiLib (`litematicaIsolation`, part of `check`, enforces this). Compiled against Litematica 0.27.14 / MaLiLib 0.28.12 as `compileOnly`; never bundled (`releaseBuild` rejects `fi/dy/masa/` entries).
- `BuildProgressCollector` (client): on the first in-world tick, checks that Litematica is loaded and that its version satisfies MinePanel's own `suggests` range, then creates the adapter. Any `LinkageError` or `RuntimeException` from the adapter disables the tile for the game session with one logged warning.

Every Litematica and world read happens on the client thread at END_CLIENT_TICK, within a 2 ms budget per tick and at most 256 chunk readiness checks per tick. Only the immutable `BuildProgress` leaves that thread.

- **Total** is the count of non-air states in the containers of the placement's enabled sub-regions (as `MaterialListUtils.createMaterialListFor`), counted incrementally without loaded chunks.
- **Scanning** works per chunk of `getTouchedChunks(PLACEMENT_ENABLED)`, comparing every position in `getBoxesWithinChunk`, and only when Litematica's verifier would: the 3×3 client chunks are loaded and the schematic world has the chunk. Each position is classified as Litematica's `checkBlockStates` does (honouring `ignoreCropAge`, `ignoreExistingFluids`, the ignore-existing-blocks list and the placement verifier's ignored mismatches, if that verifier exists). Wrong blocks, wrong states and "different block" matches all count as *wrong*, i.e. not placed. An ignored mismatch is accepted (placed, or nothing for schematic air). Schematic air with a world block is *extra*, shown only as "N to clear". Litematica's render-layer verifier range is not applied: the whole placement is compared.
- **Cache:** results per chunk, for the last four placements by hash ID; a fingerprint change (schematic, origin, rotation, mirror, enabled sub-regions and their placement) starts that placement over. `ClientLevel.setServerVerifiedBlockState` (`BlockChangeMixin`, the hook Litematica uses) and Fabric chunk loads mark already-scanned chunks for a rescan; a marked chunk keeps its last result until it is ready again. Leaving the world clears the cache.
- **Materials:** for each state, (schematic count − placed count) converted to items with `MaterialCache` as `MaterialListUtils.convertStatesToStacks` does (waterlogged blocks add a water bucket; flower pots and cauldrons need several items). *Have* sums MinePanel's own inventory snapshot (36 slots and offhand, plus shulker box, bundle and known backpack contents); it never affects placed/total.
- A selected but disabled placement is treated as no placement. Litematica's own verifier and material-list tasks are never started, so MinePanel adds no HUD renderers or chat messages.

Porting to a new Minecraft version: bump `litematica_version`/`malilib_version` in that version's `versions/<minecraft>/gradle.properties`, compare `LitematicaBuildSource` against the new `LTS/<version>` branch using the API table in [the plan](IMPLEMENTATION_PLAN.md), fix compile errors and re-run the manual checks. On 1.21.1 (Litematica 0.19) the adapter uses `getTouchedChunks()` / `getBoxesWithinChunk(x, z)` without the enabled filter, MaLiLib's `IntBoundingBox` fields instead of accessors, and no `ignoreCropAge` (that option doesn't exist there).

## Ender Storage

The `enderStorage` snapshot field (`EnderStorageSnapshot`, null without Ender Storage) feeds the **Ender Storage** panels, the inventory's ender chest slot (its icon becomes `enderstorage:ender_chest` and the dashboard opens `shown[last]`), and the item windows of Ender Pouches and Ender Storage chest items (`EnderStorage.contents(stack)`, used like backpack contents in `MinecraftInventoryCollector.item`). The `EnderStorage` facade (client, all nodes) does nothing unless, on NeoForge, `ModList` has `enderstorage`. `dev.craftyplayz.minepanel.enderstorage.EnderStorageMod` (NeoForge only) is the only code importing `codechicken` (`litematicaIsolation` enforces it). Any `LinkageError`/`RuntimeException` turns it off for the session with one warning. There is no minimum-version check.

A chest's key is `left.middle.right` (`EnumColour.getSerializedName()`), plus `.<owner uuid>` for a personal chest (`Frequency.owner()` present). Facts it relies on (Ender Storage 2.13.0.191 / CodeChickenLib 4.6.1.529, read with `javap` and from the `1.21.1` branch):

- `ContainerEnderItemStorage.chestInv` (an `EnderItemStorage`, public `freq`); the menu's first `getContainerSize()` slots are the chest (9, 27 or 54 by the server's `storageSize`). Clients get contents only while it is open (placed chest or pouch).
- Pouches and chest items carry their `Frequency` as the `enderstorage:frequency` data component (`Frequency.readFromStack`).
- Singleplayer reads use the private `EnderStorageManager.serverManager`, its `storageMap` (synchronized map, `"<Frequency.toString()>,type=item"` → storage; loaded chests) and `saveTag` (saved chests; each `{Items, size}` read with `InventoryUtils.readItemStacksFromTag`) by reflection, on the server thread, every 500 ms. `instance()`/`getStorage()` are never called: they create managers and storages. Saved-only owned chests get their owner's name from the server's profile cache.

`EnderStorage` (client thread) compares each chest it reads or sees open with the last known contents. On a change it appends one `WorldStore.EnderChange` per distinct item (`isSameItemSameComponents`, counts summed, removals first) and stores the chest; a chest opened for the first time is stored without changes. On a server, the first sight after joining is compared with the stored copy, so changes made while away are logged at that moment. The store keeps 64 chests (least recently changed dropped) with the last 500 changes each. `list` is every chest read live (singleplayer, `source` "world") or every stored one ("remembered"), up to 256; `shown` has `last` (this session's last opened, else the newest stored) plus the selections, up to 8, with the log newest first. Dashboard items are rebuilt only when a chest's contents, its stored log or the icon epoch change.

## AE2 crafting

The `ae2` snapshot field (`Ae2Snapshot`, null without AE2) feeds the **AE2 crafting** panel (`crafting`). The `Ae2` facade (client, all nodes) does nothing unless, on NeoForge, `ModList` has `ae2`. `dev.craftyplayz.minepanel.ae2` (NeoForge only) is the only code importing `appeng` (`litematicaIsolation` enforces it). Any `LinkageError`/`RuntimeException` turns it off for the session with one warning.

Facts it relies on (AE2 19.2.17, read from the JAR with `javap`). Jobs run on the server (`ExecutingCraftingJob` in `CraftingCpuLogic`, saved in the crafting CPU's block entity NBT). The client only gets:

- `CraftingJobStatusPacket(jobId, what, requestedAmount, remainingAmount, status)`. It is sent to the player who submitted a job, only at STARTED (`trySubmitJob`) and FINISHED/CANCELLED (`finishJob`). Its handler calls the static `PendingCraftingJobs.jobStatus(UUID, AEKey, long, long, Status)`.
- While a `CraftingStatusMenu` is open: `cpuList` (`@GuiSync(8)`, record `CraftingCpuList` of `CraftingCpuListEntry(serial, storage, coProcessors, name, mode, currentJob, progress, elapsedTimeNanos)`) and `selectedCpuSerial`. These refresh about once a second.
- While a `CraftingCPUScreen` is open: the incremental `CraftingStatusPacket`, merged into the screen's private `status` (`CraftingStatus`: elapsed nanos, remaining/start item counts, suspended, `CraftingStatusEntry(what, stored, active, pending)`).

Nothing requests this data without a screen, and MinePanel sends nothing. Two mixins live in their own `minepanel.ae2.mixins.json`, listed in `neoforge.mods.toml` only and left out of Fabric JARs:

- `PendingCraftingJobsMixin` (HEAD of `jobStatus`) queues each notice.
- `CraftingCPUScreenAccessor` reads `status`.

The config is `required: false` with `defaultRequire: 0`, and `Ae2MixinPlugin` applies it only when `LoadingModList` has `ae2`.

`AppliedEnergistics` (client thread, once per sample):

- **Notices:** drains the notice queue (at most 256 waiting) into the last 16 jobs. A job keeps its client-clock start time and gets an end time and result. A notice for a job that was never seen starting has `startedAt` null.
- **Screens:** while the player's `containerMenu` is a `CraftingCPUMenu`, it copies the CPU list (only from a `CraftingStatusMenu`), the selected serial and the screen's `status`, stamped `seenAt`. `open` is true only for that sample.
- **Amounts:** formatted with `AEKey.formatAmount(amount, AmountFormat.FULL)` so fluids read right.
- **Items:** shown as `wrapForDisplayOrFilter()` stacks through the normal item extraction.
- **Limits:** progress is clamped to 0–1 and rounded to 0.001. Up to 64 CPUs and 64 entries, busiest first.
- **Session:** everything is in memory and cleared by `resetSession`.

## Multiple Minecraft versions

One source tree builds a JAR per Stonecutter node, `<minecraft>-<loader>`: `26.1.2-fabric` (the `vcsVersion`, whose code is active in `src/`), `1.21.1-fabric` and `1.21.1-neoforge`. Fabric nodes run `build.gradle` (Loom through `loom-back-compat`: `fabric-loom` on 26.1+, `fabric-loom-remap` with Mojang mappings below; `loomx.modJar` is the JAR task), the NeoForge node runs `build.neoforge.gradle` (ModDevGradle; Mojang names at compile and run time, so nothing is remapped and mixins need no refmap). Both apply `gradle/shared.gradle` for tests, checks, `releaseBuild` and `installMod`. Each node's `versions/<node>/gradle.properties` holds its Java, loader/API, optional-mod coordinates, `minecraft_range` and `excluded_mixins`. On NeoForge the `client` source set is created by hand (it sees `main`, `addModdingDependenciesTo` gives it and `test` the game), and the JAR packs both.

- Loader-specific code uses the `fabric` / `neoforge` constants from `stonecutter.gradle` (`//? if neoforge {`, combinable with versions: `//? if fabric && <26.1`). Version-specific code is in `//? if >=26.1 { … } //?} else { /* … */ //?}` blocks; the inactive side is a comment in `src/` and Stonecutter swaps them in `versions/<minecraft>/build/generated/stonecutter/`. Keep each block's inactive side compiling for its version. `stonecutter.gradle` swaps `Identifier`/`ResourceLocation` and `.identifier()`/`.location()` for versions before 1.21.11.
- `fabric.mod.json` (`minecraft`, `java`, `fabric-api`) and the mixin config's `compatibilityLevel` are expanded per version. `excluded_mixins` drops mixins whose target classes don't exist on that version (1.21.1: `ItemRenderStateAccessor`, `ItemLayerRenderStateAccessor`, whose sources are also `//? if`'d out).
- 1.21.1 differences: item icons render through a `TextureTarget` and `ItemRenderer.render` as `GuiGraphics.renderItem` does and are read back with a synchronous `NativeImage.downloadTexture` (at most 16 per tick, only while icons are missing); downloaded skins and capes are read back from their GPU texture once (`HttpTexture` keeps no pixels); armor comes from `ArmorMaterial.layers()` (as `HumanoidArmorLayer`) and the elytra/cape choice from `ElytraLayer`; held-item transforms come from the `BakedModel`; the spawn sensor uses `getSharedSpawnPos()` (Overworld only); profession names use the `entity.minecraft.villager.<profession>` translation.
- NeoForge 1.21.1: `MinePanelClient` is the `@Mod(dist = CLIENT)` class; both loaders call the same private handlers. Hooks: `ClientTickEvent.Post` (tick), `ClientPlayerNetworkEvent.LoggingIn` (Fabric INIT and JOIN together; NeoForge has no hook when the listener is created) and `LoggingOut` (DISCONNECT; calls without a player are skipped), `ChunkEvent.Load` on the client level, `AttackEntityEvent` / `PlayerInteractEvent.EntityInteract(Specific)` filtered to the local player, `ScreenEvent.Init.Post` / `Closing`, `GameShuttingDownEvent` (fires inside the game loop, so a `shuttingDown` flag stops later ticks), `RegisterClientReloadListenersEvent`, and `FMLPaths`. NeoForge has no client "after block break" event: a `PlayerInteractEvent.LeftClickBlock` by the local player records the block, and if its state changed by the end of that tick it counts as mined (a different change to that exact block in the same tick would also count). No listener cancels or changes an event.
- NeoForge icons and appearance: `ItemRenderer.render` is NeoForge-patched, so custom item renderers (`IClientItemExtensions`), render passes and custom models are drawn as the GUI draws them; the icon pass saves and restores the bound framebuffer, viewport and depth test. Held-item transforms come from `BakedModel.applyTransform` (decomposed to the dashboard's translation/rotation/scale); armor textures and tints from `ClientHooks.getArmorTexture` and `IClientItemExtensions.getArmorLayerTintColor`, and items with a custom 3D armor model are skipped. Spawn eggs come from `SpawnEggItem.byId` on 1.21.1.
- Curios (NeoForge): `Accessories` asks `dev.craftyplayz.minepanel.curios.CuriosSlots` (the only package importing `top.theillusivec4.*`) for the non-empty stacks in the local player's Curios slots, which Curios syncs to the client, so it is a client-only read. They go through `MinecraftInventoryCollector.item` (so a worn backpack gets its contents) into `InventorySnapshot.accessories` (at most 32, sent whole when changed), are counted by `BuildTracker.carried`, and are shown in the Inventory panel's accessories row; their item windows use the pin source `accessory`. Singleplayer backpack contents are re-read once a second (one `server.execute` for every carried backpack; `BackpackStorage.save` only wraps the stored tags, it does not copy them).
- Backpacks panels (`backpack` Personal backpack, `backpacks` Backpacks; Minecraft 1.21.1 only, gated in the browser by `TILE_VERSIONS`): the `backpacks` details field (`BackpacksSnapshot`, null without a supported mod) holds `list` (every backpack: in singleplayer from the world's `BackpackStorage` contents and its access log (`getAccessLogs()`: name, last player, epoch-ms access time, item type, read only on the server thread), rebuilt every 5 s; on servers the backpacks remembered in the WorldStore), `last` (newest access) and `shown` (full, positional contents of the last opened backpack and of every UUID the saved layout selects: `LayoutStore.backpackSelections()` collects `backpacks.selected` from every profile's settings and from rules' set actions, at most 7). Watched backpacks (carried, `last`, selected) are re-read every 250 ms in singleplayer; on servers an open backpack screen is captured every 5 ticks. `Backpacks.collect` converts stacks to dashboard items once per contents change (`MinecraftInventoryCollector.contents`), and backpack item icons are deferred icon keys. List and shown entries carry `kind` ("backpack" or "storage") and `position` (null, or `{dimension, x, y, z}` for a placed Sophisticated Storage block; see "Container contents and Sophisticated Backpacks").
- Several Backpacks panels: `backpacks`, `backpacks2`, `backpacks3`, `backpacks4` (`BACKPACKS_PANELS` in layout.js and LayoutStore) all read the one `backpacks` snapshot field; each has its own `<id>.selected` setting, search text and fold state (`backpacksPanel(id)` in features.js; the markup for all four is in index.html because app.js looks tiles up before features.js runs). `LayoutStore.backpackSelections()` collects `selected` from all four in every profile and from rules' set actions on any of them (at most 7 watched). List and shown entries carry `kind` (`backpack`/`storage`) and `position` (null for backpacks; dimension and x/z within ±30,000,000, y within -2048..2048 for storages).
- Ender Storage panels (`enderStorage` to `enderStorage4`; Minecraft 1.21.1 only, via `TILE_VERSIONS`): the `enderStorage` details field, see "Ender Storage". Selections come from `LayoutStore.enderStorageSelections()` (same rules as backpacks, at most 7).
- Backpack nicknames: the top-level layout field `backpackNames` (lowercase UUID or Ender Storage chest key → 1–64 characters, at most 256; global, not per profile) is validated in both validators and only renames things on the dashboard. It is never sent to the game and isn't part of a rule set export.
- Optional mods on NeoForge are declared `optional` with any version in `neoforge.mods.toml` (a range would stop the game from starting with an older one); the minimums are `[modproperties.minepanel]` entries that `BuildProgressCollector` and `Backpacks` compare at run time. Forgematica registers the mod id `litematica` and keeps Litematica's `fi.dy.masa` packages, so `LitematicaBuildSource` compiles unchanged against it.
